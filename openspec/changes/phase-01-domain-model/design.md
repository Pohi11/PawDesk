# Design

## Context

The backend is a FastAPI app with no persistence layer yet. It has typed settings, a `/health/db` probe that uses psycopg directly, and tests that run against the Postgres 18 container from `docker-compose.yml`. Day-to-day development runs Postgres in Docker and the backend on the host (see [decision record 0002](../../../docs/decisions/0002-local-dev-topology.md)). See `proposal.md` for motivation and `specs/` for the required behavior.

Later phases constrain this design:
- The orchestrator (Phase 6) runs model calls concurrently with `asyncio`, persists state after every step, and resumes after a crash.
- The dashboard (Phase 9) reads the transition log and spans.

## Goals / Non-Goals

**Goals:**
- The database rejects invalid data on its own (constraints, not just application checks) wherever a rule can be expressed in SQL.
- Lifecycle rules live in one small module with no database or I/O dependencies, so every (from, to, actor) combination can be tested exhaustively in milliseconds.
- Tests run against a real migrated schema, isolated from development data.

**Non-Goals:**
- HTTP endpoints for these records.
- Compliance or capacity logic (Phase 2).
- Orchestration and resume (Phase 6).
- Soft deletes.
- Multi-tenant authorization.
- Matching an incoming message to an existing owner. Seeded requests reference a known owner.

## Decisions

### D1. Async SQLAlchemy 2 with the psycopg 3 driver
Database access uses SQLAlchemy 2's async engine (`postgresql+psycopg://`), so the asyncio orchestrator never blocks the event loop on a database call. Relationships default to `lazy="raise"`. An accidental implicit load fails loudly instead of triggering a hidden query, which async SQLAlchemy cannot run anyway.
- *Alternatives:* sync SQLAlchemy run in a thread pool (simpler, but every database call from async code needs wrapping); SQLModel (thin layer on SQLAlchemy that lags behind it); raw SQL (no unit of work, no migrations autogenerate).
- This choice applies to every later change. It is recorded as [decision record 0003](../../../docs/decisions/0003-async-database-access.md).

### D2. UUIDv7 primary keys generated by Postgres
Every table's primary key is a `uuid` with server default `uuidv7()`, which is built into Postgres 18. UUIDv7 values are time-ordered, so inserts append to the index like a sequence does. IDs can be created anywhere without coordination, which matters for trace and span IDs, and they can't be guessed by counting the way sequential integers can.
- *Alternatives:* `bigint` identity (smaller, but enumerable and awkward for traces); UUIDv4 (random order spreads inserts across the index).
- *Trade-off:* a UUIDv7 reveals its creation time, which is acceptable for this data.

### D3. Enumerations as text with CHECK constraints
Species, service, size class, lifecycle state, actor, span kind, span status, and approval action are Python `StrEnum`s. They are stored as `text` columns constrained by a `CHECK`, using SQLAlchemy's non-native enum.
- *Alternative:* native Postgres `ENUM` types. Values can't be removed or renamed without recreating the type, and that makes migrations painful as the lifecycle evolves.

### D4. Size class as a generated column
`pets.size_class` is `GENERATED ALWAYS AS (CASE … END) STORED`, computed from `species` and `weight_lb` with the thresholds in the spec. The database computes it on every insert and update, so it can never be entered by hand or drift from the weight.
- *Alternative:* a Python setter or ORM event. That can be bypassed by raw SQL or bulk updates, and it would be a second place where the rule lives.
- Later phases read size class from the pet row and never recompute it.

### D5. Reservation overlap prevented by an exclusion constraint
`reservations` has `EXCLUDE USING gist (kennel_id WITH =, daterange(start_date, end_date, '[)') WITH &&)`, which needs the `btree_gist` extension. The half-open range `[start, end)` means a stay is the nights from check-in up to checkout, so back-to-back stays don't conflict. `CHECK (end_date > start_date)` rules out zero-night stays. A unique constraint on `booking_request_id` (nulls allowed) prevents double-booking when a step is retried.
- *Alternatives:* checking for overlaps in application code (two concurrent requests can both pass the check, then both insert); `SELECT … FOR UPDATE` locking (correct, but every caller has to remember to do it).

### D6. Lifecycle in two layers: a pure guard and a transition service
- **Guard** (`app/lifecycle.py`). `State` and `Actor` enums, the explicit set of allowed transitions, and a function that takes the current state, target state, actor, and recorded failed step. It returns normally if the transition is allowed and raises `IllegalTransition` naming both states otherwise. No I/O. The retry rule (from `failed` only back to the recorded failed step) is the one case that depends on data beyond the three-part combination.
- **Service** (`app/transitions.py`). An async `transition(session, request, target, actor, reason=None, error=None)` that:
  1. calls the guard,
  2. updates the state,
  3. sets or clears `failed_step` and `last_error`,
  4. appends the transition-log row, and
  5. flushes.

  The caller owns the commit, so a step's output, its state change, and its log row all land in one transaction.
- *Why this split:* the rules that make the system safe ("nothing but `ready`/system or `needs_review`/staff reaches `approved`") are a plain data table that can be read and tested without a database.

### D7. Optimistic concurrency with a version column
`booking_requests.version` is SQLAlchemy's `version_id_col`. Every update includes `WHERE version = :loaded_version`. If no row matches, SQLAlchemy raises `StaleDataError`, which the service turns into `TransitionConflict`. Because the transaction rolls back, the conflicting update writes no log row.
- *Alternative:* pessimistic `SELECT … FOR UPDATE`. That holds a row lock for the whole step, and steps include model calls that take seconds.

### D8. Failure state is consistent by construction
`booking_requests` has `failed_step` and `last_error`, with `CHECK ((status = 'failed') = (failed_step IS NOT NULL))`. A failed request without a recorded step, or a recorded step on a request that isn't failed, can't exist.

### D9. Trace and span integrity in the schema
- `spans` has a unique constraint on `(trace_id, id)`. A composite foreign key `(trace_id, parent_span_id) → spans(trace_id, id)` makes a parent from another trace impossible. With the default MATCH SIMPLE, a null parent skips the check.
- `cost_usd` is `NUMERIC(14,10)`, which is exact. Floats can't represent amounts like 0.0000942 exactly, and totals drift.
- `input` and `output` are `JSONB`.
- CHECK constraints cover: non-negative tokens and cost, `ended_at >= started_at`, and `status = 'error'` requiring an `error` message.

### D10. Smaller rules as CHECK constraints or ORM validation
- **CHECK constraints in SQL:** `weight_lb > 0`, `expires_on >= administered_on`, a `reject` approval requires a reason, and unique `(facility_id, service, species, vaccine)` rules.
- **ORM validator:** the facility time zone is checked with `zoneinfo`, because a CHECK constraint cannot consult the IANA database.

### D11. Migrations
Alembic uses the async template. The initial migration is autogenerated, then reviewed and edited by hand, because autogenerate does not detect the extension, the exclusion constraint, the generated column, or the composite foreign key. The backend container runs `alembic upgrade head` before starting uvicorn, so `docker compose up` always serves a current schema.

### D12. Test database and isolation
- **Setup:** Tests use a separate `pawdesk_test` database on the same server. A session-scoped fixture creates it if it's missing, then runs `alembic downgrade base` followed by `alembic upgrade head`. Every run exercises both the downgrade and upgrade paths.
- **Isolation:** Each test runs inside an outer transaction that is rolled back at the end, using SQLAlchemy's "join an external transaction" pattern with savepoints. Code under test can still commit.
- **Async:** pytest-asyncio with `asyncio_mode = auto`.

### D13. Spec-to-test traceability
Each test that verifies a requirement carries `@pytest.mark.spec("<capability>", "<requirement name>")`. The marker is registered in `pyproject.toml`, and a `conftest.py` hook copies it into JUnit XML properties so results can be joined to specs later. The convention applies to every later change and is recorded as [decision record 0004](../../../docs/decisions/0004-spec-test-traceability.md).

### D14. Seed command
`uv run python -m scripts.seed`:
1. Refuses any host other than `localhost`, `127.0.0.1`, or `postgres`.
2. Truncates every domain table in a single `TRUNCATE … CASCADE`.
3. Inserts a fixed, fictional dataset in one transaction.

Dates are computed relative to the day the seed runs, so "expires during an upcoming stay" stays true whenever the seed is run.

## Risks / Trade-offs

- [The generated column's thresholds live in SQL] → Size class is read from the database everywhere and tests pin each boundary, so there is only one copy of the rule.
- [`lazy="raise"` makes forgotten eager loads fail at runtime] → That's intentional: it fails loudly in tests instead of silently issuing N+1 queries. Queries use `selectinload` explicitly.
- [Bulk `UPDATE` statements bypass `version_id_col` and the guard] → State changes only go through the transition service. A test asserts that the log row and the state change move together.
- [Autogenerate misses hand-written constructs] → The migration is reviewed by hand, and the downgrade/upgrade round trip runs on every test session.
- [Relative seed dates make demo data differ from day to day] → The scenarios (expired, expiring mid-stay, no expiry) are what's stable. Tests assert on scenarios, not specific dates.

## Migration Plan

This is a new schema with no existing data. Deploy by running `alembic upgrade head`. Roll back with `alembic downgrade base`, which only makes sense in development since it drops every table. The compose backend runs migrations at startup.
