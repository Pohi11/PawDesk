# Proposal

## Why

The first certificate benchmark (v1) measures field accuracy well, but its decision metric is weak. For the reference stay, the correct compliance outcome is `not_compliant` for 28 of 36 certificates, `compliant` for 5, and `needs_review` for 3, because randomly drawn dates are usually expired. A records step that leaned toward "not compliant" would score almost perfect decision agreement on v1 while being dangerous in practice. Decision agreement only means something when the correct answers are mixed, and when many certificates sit right at the boundary where a one-day misread flips the result.

## What Changes

- Add benchmark **v2**: 36 certificates, the same layouts and variants, generated by first choosing each certificate's correct decision and then constructing records that produce it. The mix is balanced across `compliant`, `not_compliant`, and `needs_review`, with deliberate boundary cases (an expiry on checkout day versus the day before).
- The generator checks every v2 certificate's decision against the compliance check before writing anything.
- Keep **v1 unchanged** alongside it, so earlier reports stay reproducible. Each truth file names its benchmark version, and evaluation reports name the version they ran on. The evaluation defaults to the newest benchmark.

## Capabilities

### New Capabilities
- None.

### Modified Capabilities
- `certificate-evaluation`: adds requirements for balanced reference decisions with boundary cases, and for keeping benchmark versions side by side. The existing requirements apply to every version unchanged.

## Impact

- **Backend:** `scripts/generate_certificates.py` gains a v2 truth generator and a version argument. `scripts/eval_records.py` gains a version argument and records the version in its report. New committed assets go in `backend/evals/certificates/v2/`.
- **No runtime code changes.**
- **Cost:** one real-model evaluation run on v2 (cents).
